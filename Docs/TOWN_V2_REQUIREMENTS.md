# AIFarm Town V2 需求规格

## 1. 文档状态与目的

本文记录 AIFarm 四居民小镇 V2 的实现合同与验收要求。功能是否通过以当前代码、自动化测试和 `TOWN_V2_ACCEPTANCE_TESTS.md` 的证据为准，文档不得用历史审计状态替代实际验证。

`origin_requirements.md` 中的自然语言入口、播种、浇水、施肥、除草、收获、时间、背包与自然角色表现仍是产品主线。`AGENTS.md` 的 **Multi-resident invariants** 是不可放宽的上位约束；本文将其收敛为可实施且可验收的 V2 范围。若本文、实现或其他 V2 文档发生冲突，应先满足 `AGENTS.md`，再修正文档使其一致。

需求使用 `TV2-*` ID；对应的可执行验收见 `TOWN_V2_ACCEPTANCE_TESTS.md`。架构、演示和远程调用预算分别见 `TOWN_V2_ARCHITECTURE.md`、`TOWN_V2_DEMO_SCRIPT.md` 与 `TOWN_V2_AI_BUDGET.md`。

## 2. 当前实现合同

下表概括当前四居民实现必须持续满足的合同。

| 主题 | Town V2 实现合同 |
| --- | --- |
| 场景与身份 | 固定芽芽、阿木、小穗、墨墨四名居民；任何运行时归属都使用稳定、不透明的 `ResidentId`。 |
| 运行状态 | 注册表按 `ResidentId` 保存四个独立运行上下文；不存在可变的全局“当前居民”。 |
| 人设与记忆 | 每名居民有独立人设、私有记忆、目标、日程和版本；跨居民读取默认拒绝。 |
| 农田与背包 | 保留同一个共享 Unity 权威世界；四名居民通过原子提交和点位预约安全协作。 |
| 对话 | 支持严格轮次、互斥、超时和可取消的双人会话，不支持三人以上群聊。 |
| 调度 | 每名居民有按 ID 隔离的确定性日程；时间边界触发离散调度事件。 |
| AI | 所有远程调用经共享协调器，按居民限流，携带所有者与版本，严格校验并可回退。 |
| 点位并发 | 任一世界交互点同一时刻最多被一个居民以租约令牌预约。 |
| 存档 | V4 按稳定 ID 保存四居民和 12 条有向关系；允许进行中保存，但不持久化活动 Conversation/TownEvent、path、lease 或 in-flight request；已实际播放的对话片段只投影为双方各自的 private memory。 |

当前实现继续保留 Unity 权威农田/时间/背包、确定性农事动作、响应白名单校验、离线回退、观察/记忆/反思和旧存档迁移。四居民能力必须通过显式 ID 和共享协调器运行，不能依赖隐含的“当前 NPC”。

## 3. V2 固定参考配置

### TV2-SCP-01 四居民与共享世界

参考演示固定注册以下四名居民：

| ResidentId | 初始显示名 | 说明 |
| --- | --- | --- |
| `resident-001` | 芽芽 | 显示名沿用 MVP 角色 |
| `resident-002` | 阿木 | 第二名可观察居民 |
| `resident-003` | 小穗 | 第三名可观察居民 |
| `resident-004` | 墨墨 | 第四名可观察居民 |

`ResidentId` 是不透明身份键；显示名、本地化文本、GameObject 名称、列表下标和生成顺序都不得作为身份。显示名可以修改，不能因此改变状态归属。参考场景仍只有一块共享 3×3 农田、胡萝卜一种作物、一份共享演示背包和一个共享游戏时钟。

### TV2-SCP-02 固定农务初始与最终状态

参考农务流程从第 1 天 08:00、九块空地、共享背包“胡萝卜种子/水/肥料/胡萝卜 = 9/9/9/0”开始。每块地成功消耗 1 粒种子、1 份水和 1 份肥料，并最终产出 1 个胡萝卜；流程结束时九块地回到空闲，背包必须为 `0/0/0/9`。

### TV2-CMP-01 四居民协作农务闭环

玩家可发布显式的**公开城镇农务目标**。本地确定性分派器必须按下表分片，且在播种、浇水、施肥、除草和收获每个阶段始终使用相同分片：

| 居民 | 固定地块 |
| --- | --- |
| `resident-001` | 1、5、9 |
| `resident-002` | 2、6 |
| `resident-003` | 3、7 |
| `resident-004` | 4、8 |

每名居民在自己的分片内按地块号升序执行；四名居民可以并发执行互不冲突的原子动作。阶段之间设置全局屏障：九块地全部成功完成当前阶段后，任何居民才可进入下一阶段；杂草与成熟仍只由权威游戏时间和确定性规则触发。分派、阶段推进、等待和动作顺序不得由模型决定。

### TV2-CMP-02 MVP 规则回归

播种、浇水、施肥、除草、收获的前置条件、库存扣减、时间生长和非法动作不变更状态等 MVP 领域规则必须继续通过自动化回归。Town V2 的“四居民”场景取代 MVP 的“恰好一名 NPC”场景断言，但不得削弱农务闭环或离线能力。

## 4. 身份、状态与命令路由

### TV2-ID-01 稳定且唯一的身份

每名居民必须有非空、稳定、唯一的 `ResidentId`。注册、创建新演示、存档/读档、场景重载和显示名变化后 ID 均保持不变。重复、缺失或未知 ID 必须在改变运行状态前被拒绝，并产生不含私有内容的诊断事件。

### TV2-ID-02 显式寻址且无全局当前居民

居民注册表、命令、事件、动作、会话、预约、AI 请求和存档 API 必须接收或携带明确的 `ResidentId`。系统不得存在可变的全局 `CurrentResident`、`CurrentNpc` 或等价隐式权威。UI 可以有“当前查看/选择项”，但提交命令时必须把所选 ID 复制进不可变命令信封；之后切换 UI 选择不得改变该命令的归属。

### TV2-ISO-01 私有运行状态按 ID 隔离

运行状态、私有记忆、目标、日程、行动队列、会话占用、反思、AI 请求所有权和生命周期版本必须按 `ResidentId` 保存和查询。一个居民的清空、失败、取消、重规划或读档不得覆盖另一居民的私有状态。

### TV2-CMD-01 定向输入与公开输入

玩家输入必须明确是：

- `PrivateToResident`：仅送达一个已验证的 `ResidentId`；或
- `PublicTownEvent`：显式标记为公开，并由本地分派器确定接收者。

未标记的输入不得被自动广播。公开农务目标由四个固定居民接收，并生成四个按 ID 归属的子目标；模型不能扩大接收范围或改派地块。

参考配置中，公开命令若启用可选远程解释，只允许一个解释请求，并由本地确定性协调器指定 `resident-001` 为 `RequestOwner`。该请求只能包含公开原文、公开只读信息和本次允许意图，不能读取或发送 001 的私有记忆；只有响应被校验为 `CompleteCarrotLifecycle` 后，Unity 才发布 `PublicTownEvent`。失败或回退时由同一规则的本地解释器发布事件。`RequestOwner` 只是请求记账归属，不赋予 001 改派、独占或私有化公开目标的权力。

## 5. 共享世界、动作与预约

### TV2-WLD-01 单一权威与原子提交

农田、共享背包、游戏时间和可交互点状态只有一个 Unity 权威来源。居民的计划和模型响应只是候选意图；每个原子动作必须在开始前和提交前再次检查权威前置条件。失败动作不得部分修改位置以外的领域状态，不得重复扣减库存或重复产出。

### TV2-ACT-01 每居民行动互斥

每名居民最多有一个活动世界动作。V2 参考策略还要求“活动世界动作”和“活动会话”互斥：正在会话的居民不能开始世界动作，正在执行原子动作的居民不能加入会话；新请求必须由本地协调器确定性地等待或拒绝，不能中断已开始的原子提交。

### TV2-RSV-01 交互点唯一预约

任一世界交互点同一时刻最多由一名居民预约。预约必须返回绑定 `ResidentId`、点位 ID 和代次的不可伪造令牌；只有持有者可续期、使用或释放。竞争同一点位时，协调器按“请求入队序号，再按 ResidentId 字典序”裁决，失败者等待或重新规划，不能穿透预约执行。

### TV2-RSV-02 预约生命周期

预约必须在动作完成、失败、取消、超时、居民禁用、新演示、场景卸载和读档时释放或失效。陈旧令牌不能释放新租约。读档后只能根据恢复后的权威状态重新申请，不得盲目恢复旧令牌。

## 6. 日程、感知与知识边界

### TV2-SCH-01 独立且确定性的日程

每名居民有按 `ResidentId` 归属的日程条目，至少包含游戏时间段、白名单高层活动和逻辑目标位置。时间系统跨越日程边界时发出一次离散事件；同一边界不得因多帧 `Update()` 重复触发。参考优先级固定为：完成已开始的原子动作或会话 → 已接受的公开农务子目标 → 到期日程 → Idle。模型不能写入或修改日程。

### TV2-KNW-01 私有记忆访问控制

每条私有记忆必须具有所有者 `ResidentId`、来源、游戏时间和可见性。居民只能查询自己的私有记忆；构造该居民的 AI 上下文时也只能使用其私有记忆与对其可见的公开事实。跨居民私有读取必须明确失败，而不是返回空值后静默继续。

### TV2-KNW-02 合法学习渠道

居民只能通过以下渠道学到新信息，并保留来源：

1. 自身感知范围内的权威世界事件；
2. 自己参与的会话中已经实际说出的内容；
3. 明确定向给自己的玩家输入；
4. 显式标记的 `PublicTownEvent`。

全局日志的存在不等于所有居民都已感知。未参与会话的第三名居民不能获得会话内容；一个居民可在后续会话中转述自己已合法得知的信息，此时接收者的来源是该次会话。

### TV2-KNW-03 事件可见性

事件必须声明 `Private`、`Participants` 或 `PublicTown` 可见性，并携带产生者/接收者 ID（适用时）。观察系统根据可见性和感知结果逐居民投递，禁止把全部世界事件无条件复制到四份记忆。

## 7. 受约束的小镇共同活动

### TV2-EVT-01 固定 HarvestDinner 与非权威提案

第一版只有一个活动定义：稳定 `ActivityId=town-event-harvest-dinner`、类型 `HarvestDinner`、开始时间为提案时刻之后的下一次有效 18:00、地点为广场的稳定 `TownLocationId`。模型输出只包含高层意图 `propose_town_event` 及受限理由，不包含活动类型、时间、坐标或参与者。Unity 在模型输出之外附加提案者、可传播知识 ID、实际会话来源和提案游戏时间，构造非权威 `TownEventProposal`，并固定映射到 HarvestDinner。

### TV2-EVT-02 唯一协调器与单活动约束

`TownEventCoordinator` 是 proposal 校验、邀请、集合、开始、推进、结束和清理的唯一入口。上游请求协调器先校验 RequestId、owner 和版本；活动协调器再校验提案者已注册、来源知识属于提案者、该知识是实际双人会话中获得的可传播胡萝卜收获事实、来源会话匹配、事实未被用于旧活动，以及当前没有非终态活动。幂等和重复防护依据可传播事实根、会话证据与当前活动状态，不依赖独立提案标识。全镇任意时刻最多一个处于 `Scheduled`、`Gathering` 或 `Active` 的共同活动。

### TV2-EVT-03 全镇邀请、可选参加与正常到达

HarvestDinner 必须公开邀请芽芽、阿木、小穗、墨墨四名固定居民，但邀请者集合与实际参加者集合必须分离。第一版本地规则让提案者和向其传递本次收获事实的直接会话来源进入 `Accepted`，其余未参与该次信息交流的受邀者进入 `Declined`；18:00 复核时不能中断当前状态者改为 `Unavailable`。领域层仍保留 `Pending`，集合开始时尚未回应的 `Pending` 按拒绝处理。模型不能直接写参加决定，也不能借活动修改常规日程。开始集合至少需要 **2 名**已接受且可参加的居民。

只有接受邀请的居民获得 attendance task，并通过 NavMesh 正常前往广场、预约各自不同的 attendance point；禁止瞬移。居民到达后播放其本地配置的面向、姓名/状态图标和简单到达表现。活动只在本次所有已接受参加者均持有有效预约并到达后开始；任一实际参加者导航失败、预约丢失或到达超时都可以安全取消整场活动，并必须释放全部活动预约和状态，不能要求剩余两人继续，也不能等待模型裁决。

### TV2-EVT-04 公共表现与受约束双人短会话

活动开始后必须播放一次确定性公共欢迎语。双人短会话是可选增强；若启用，只能在活动定义的固定有界上限内安排，每段从实际到场居民中选择恰好两人并通过现有 `ConversationCoordinator`，仍遵守参与者锁、2–6 句、墙钟超时、实际播放才写记忆和结束释放。同一居民同时最多进入一段，普通社交不得抢占活动参加者，活动子会话也不得与居民的其他动作或会话重叠。

活动不是自由多人群聊。禁止三人或四人话轮、群聊 AI 请求、群聊正文记忆、自动旁听其他配对正文，或由模型创建/邀请不存在的居民。

### TV2-EVT-05 公共事实与私人参加记忆隔离

活动邀请和活动实际开始分别作为 `PublicTownEvent` 投递，四名居民可以合法记住这些公共事实，但公共事实不能被当作“某居民实际参加”的证明。每名实际到场并完成活动的居民必须分别写入 owner 为自己的私人 `TownEventCompleted` 记忆，记录 ActivityId、地点、来源事件和自己的有限视角；活动内双人会话正文只写给对应两名参与者。

拒绝、未响应、导航失败或未到场的居民不得获得“我参加了 HarvestDinner”的私人记忆，但可以保留合法收到的公共邀请/开始事实。取消的活动不得写完成参加记忆。活动结束、取消、导航失败、居民禁用、场景卸载和读档都必须幂等释放活动租约、点位预约及关联会话；网络不可用时同样由 Unity 本地规则完成或安全取消。

## 8. 成对会话

### TV2-CON-01 会话身份与互斥

活动会话具有唯一 `ConversationId`、两个不同的参与者 ID、当前说话者、已用话轮数、开始时间、截止时间和状态。每名居民最多参加一个活动会话；任一参与者已在会话中时，新的会话请求必须失败或确定性排队，不能创建重叠会话。会话只允许两个参与者，且双方轮流发言。

### TV2-CON-02 严格话轮与超时

一次居民发言被接受并展示即计 1 个话轮，本地回退发言同样计数。每场成对会话最多 **6 个话轮**，总墙钟时间从会话进入 Active 起最多 **30 秒**；任一限制先到即结束。结束必须释放两名居民的会话占用和相关预约，取消或作废在途请求，并记录结构化结束原因。不得为了生成告别语突破限制或追加远程调用。

### TV2-CON-03 对话内容边界

模型只能产生受长度、角色和会话 ID 约束的候选话语/情绪；Unity 会话状态机决定说话者、轮次、参与者和结束。有效话语仅写入两个参与者各自的私有记忆，并记录共同的公开元数据（不含全文）；第三名居民不会自动获得正文。

## 9. AI 边界、协调与回退

### TV2-AI-01 共享网关与离散触发

所有远程 AI 调用必须通过一个共享 AI 网关和请求协调器。居民、MonoBehaviour、对话气泡和行动执行器不得直接连接模型。逻辑请求只能由用户提交、日程边界、会话轮次、动作/目标结果等离散事件创建；不得从任何 `Update()` 中创建或启动远程调用。`Update()` 只可推进本地表现、时钟或已经存在的本地状态机。

### TV2-AI-02 请求所有权、上下文与关联

每个逻辑 AI 请求必须携带唯一 `RequestId`、所有者 `ResidentId`、操作类型、所有者生命周期版本、关联的 Goal/Conversation ID（适用时）、入队单调时间、绝对截止时间和有界只读上下文。响应必须与这些字段匹配才能进入校验；提示和上下文不得包含另一居民的私有记忆、凭据或不受界定的完整世界快照。

所有操作都必须有居民所有者，不允许用 `town`、空值或显示名绕过按 ResidentId 的归属。公开命令解释按 `TV2-CMD-01` 固定归属 `resident-001`；成对会话的当前说话者是当前话轮的请求所有者。

### TV2-AI-03 严格 Schema 与意图白名单

每个模型响应必须做严格 Schema 校验：拒绝未知字段、缺失字段、类型强制转换、越界长度、未知居民/资源、错误关联 ID 和非白名单枚举。V2 可执行高层意图白名单仅为：

- `CompleteCarrotLifecycle`；
- `propose_town_event`；
- `RequestConversation`；
- `ContinueConversation`；
- `Idle`。

表达和反思使用独立的非执行 Schema。目标居民、会话参与者和逻辑资源还必须属于 Unity 在该请求中明确提供的候选集合。未知意图或非法目标一律拒绝并走本地回退。

### TV2-AI-04 模型不得直接改变世界

模型不得输出或直接修改位置、路径、动作序列、交互点令牌、游戏时间、背包、农田、关系值、日程、记忆所有权或存档，也不得瞬移居民。Unity 只能把已验证的高层意图交给本地确定性分派器/规划器；`propose_town_event` 只能形成待校验 proposal，不能直接创建或开始活动。全部领域变化仍经 `TV2-WLD-01` 的前置检查和原子提交。

### TV2-AI-05 三秒端到端期限与确定性回退

每条远程路径都必须有可独立完成同一状态机步骤的确定性本地回退：命令解释用本地白名单解析，表达/反思/会话话轮用角色模板，日程和行动决策用本地规则。远程请求的 **3 秒**期限从逻辑事件或用户提交进入协调器队列时开始，包含排队和传输；到期后必须取消或忽略远端结果并立即采用本地结果，不得再额外等待。断网、拒绝、限流、异常、无效 Schema 和预算耗尽采用同一路径，且不能冻结主循环。

### TV2-AI-06 并发与预算

协调器同时最多启动 2 个远程请求，同一 `ResidentId` 同时最多 1 个。默认远程预算采用 10 分钟滑动窗口，覆盖全部操作：最多 12 个请求、18,000 输入 token、3,000 输出 token；详细 operation 配额、计量、保留量、公平性和降级规则以 `TOWN_V2_AI_BUDGET.md` 为准。排队不能延长 3 秒端到端期限；无法在期限内获得槽位或预算时直接本地回退。

### TV2-AI-07 陈旧请求处理

居民重规划/取消、目标或会话结束、所有权版本变化、新演示、场景卸载或读档时，相关在途请求必须尽力取消；无法取消的响应必须被忽略。陈旧响应不得显示话语、写记忆、启动动作、改变目标或提交任何世界状态。忽略行为必须可由 `RequestId`、`ResidentId` 和原因审计。

## 10. 存档、可观察性与安全

### TV2-SAV-01 V4 多居民存档身份完整性

当前多居民格式（实现版本 `4`）必须只保存一份共享世界、恰好四条按 `ResidentId` 归属的居民记录，以及完整的 12 条有向关系边。居民记录包含规范定义引用、运行状态、私有记忆、目标、可恢复行动意图和可用的场景位置；确定性日程定义来自 Unity 配置，不复制到存档。加载前先完整校验版本、固定四 ID 的唯一性/完整性、规范显示名、记忆 owner、关系方向与完整边集、所有外键、白名单枚举、长度与数值范围；任何错误都必须在权威重置前整体拒绝，不能部分覆盖当前世界。

Save 在居民对话、日程移动、HarvestDinner 或远程请求进行中仍可生成稳定快照，但不得为了保存而推进或取消现场状态。若活动双人会话已经实际显示至少一句，保存器必须在双方各自 `MemoryStore` 的临时克隆中投影一条 owner 隔离、不可共享的 private `ConversationInterrupted` 记忆；内容只能来自保存点前实际播放的台词，并分别记录对方为即时信息来源。该投影不得修改正在运行的 MemoryStore 或会话。`ConversationId` 可以作为已提交摘要或这类投影记忆的 provenance `sourceEventId` 出现在快照中，但不能作为可恢复的 active 状态，也不能据此恢复会话。

除上述已播放片段投影外，快照只包含保存时已经提交的世界结果、owner 正确的记忆、关系和可恢复意图；绝不包含 `ConversationSession`、未播放台词、未应用 outcome、话轮游标、TownEventSession、参加者任务、deadline、锁、NavMesh 路径、有效预约令牌、coroutine 或 pending/active 网络请求。保存期间发生的迟到结果只能由正常运行态处理，不能改写已捕获快照。

### TV2-SAV-02 安全恢复

在途 AI 请求和预约令牌不写入存档。Load 不得从文件重建、续播或推进 Conversation/TownEvent/NavMesh 路径。加载器必须先把主档读入临时模型并完整校验；主档损坏或不受支持时，只能改为读取并完整校验最近备份。只有选出合法快照且即将应用时，才允许跨越权威重置边界；主档和备份都不合法时必须保留当前现场和原文件，提示用户重试或显式新建 Demo，不得自动删档、自动清空世界或留下半应用结果。

权威重置必须递增全局状态 revision，取消所有居民的 pending/active AI ticket，立即释放共享并发槽和 ResidentId owner，并让目标解释、表达和反思等父 coroutine 同时失效。父 coroutine 必须以自己的 generation 和捕获的权威 revision 双重校验后才能清标志或应用结果，因此被取消的子传输即使稍后恢复也不能覆盖新状态。随后结束加载前现场的 transient 会话与活动、失效会话锁及全部预约、取消移动并清除 Busy/InConversation/TownEvent suspension；清理必须容忍会话参与者对象已销毁、Anchor 只剩孤儿预约或 TownEvent 地点/席位失效。恢复世界、四份运行态/记忆/位置和 12 条有向关系后，未完成农务及当前日程从最后已提交状态重新检查、重新规划和重新预约，不能重复扣减、产出、瞬移或令居民永久停在 Busy/InConversation。

旧 V1 单居民存档必须把原 NPC 数据迁移为芽芽 `resident-001`，补齐另外三名规范居民和完整的 12 条默认有向关系；V2/V3 也只经显式迁移器扩为同一固定四居民图。迁移后再次保存必须写为 V4，且记忆 owner 与关系方向不得串线。

### TV2-OBS-01 居民级可观察性

UI 必须显示四个居民的显示名与 ResidentId、当前高层目标、日程活动、动作、会话对象/话轮、AI 模式和失败/回退状态，并显示共享时间、背包和农田阶段。结构化日志至少包含事件类型、ResidentId、Goal/Conversation/Request ID、点位 ID 和结果（适用时），足以证明隔离、预约和陈旧响应处理。

### TV2-OBS-02 可观察性不破坏隐私

公共 HUD 和共享日志不得输出私有记忆正文、完整私聊正文、提示、密钥或认证头。玩家可通过明确的调试/检视操作查看某一居民的私有记忆，但该 UI 选择不是其他居民的读权限，也不是运行时“当前居民”。

### TV2-SEC-01 凭据与数据最小化

API 密钥只来自环境变量或被忽略的本地配置，不得进入 Unity 资源、源代码、存档、日志或文档示例。每次远程调用只发送完成该操作所需的有界、只读、按所有者过滤的快照。

## 11. 非功能要求

### TV2-NFR-01 离线与演示时限

核心 V2 不需要网络、API 密钥或 Python 服务。FastAPI 不可达时，公开四居民农务流程必须从提交起在 120 秒真实时间内完成并得到 `0/0/0/9`；一次成对会话也必须使用本地模板正常闭合；合法安排的 HarvestDinner 必须能按本地时钟集合、播放必需欢迎语并完成，或在人数/导航/预约/到达约束失败时安全取消。

### TV2-NFR-02 确定性与稳定性

相同初始存档、相同公开目标、相同时间事件和相同本地模式必须得到相同居民分片、阶段序列、状态提交和最终结果。参考场景应在本地模式连续运行 10 分钟真实时间，无未处理异常、死锁、重复预约、重叠会话、居民双动作或跨居民记忆泄漏。

### TV2-NFR-03 主线程响应

网络等待、预算等待和对话等待不得阻塞 Unity 主线程。UI、时钟暂停/恢复和本地居民表现必须在远程请求进行期间继续响应。

## 12. 范围内与明确非范围

Town V2 范围内：固定四居民注册与表现；稳定身份；居民级状态、记忆、目标和日程；`SocialGraph` 与确定性关系更新；一块共享 3×3 胡萝卜田与共享背包；确定性协作分派；点位预约；有界成对会话；唯一受约束的 HarvestDinner 共同活动；共享 AI 协调、预算、Schema 校验和离线回退；V2 存档迁移；居民级可观察性与测试。

本版本不包括：动态增删居民、三人以上群聊或自由多人群聊、多人联网、恋爱/婚姻、经济、天气、动物、战斗、多作物、程序化城镇、复杂职业或生活模拟、语音、云存档、向量数据库、模型生成低层动作、模型自主修改日程/存档或正式美术。显示出自然差异不要求建立通用人格生成系统；四个固定人设和确定性本地模板即可。

## 13. 完成定义

Town V2 只有在以下条件全部满足时才可声明完成：

1. `TOWN_V2_ACCEPTANCE_TESTS.md` 中所有 Mandatory 测试通过并保存证据；
2. 现有农务领域与离线回归仍通过，公开协作流程在 120 秒内得到共享背包 `0/0/0/9`；
3. 四名居民的 ID、私有状态、记忆、目标、日程、请求和存档均可证明隔离；
4. 动作、会话、点位和远程调用的并发上限可证明，陈旧响应不可产生副作用；
5. 关闭远程服务仍能完成农务、日程、成对会话和 HarvestDinner 的参考演示；
6. 文档与实际行为一致，没有把可选在线表现描述为核心运行前提。
